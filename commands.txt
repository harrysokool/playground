Key Finding: The 229-Firm Outlier Is a Data-Quality Artifact, Not a Real IA Code; Names Are Not Individual-Specific
The single most important discovery: the "IA code appearing under 229 firms" is an empty string masquerading as a valid value, not a genuine credential. Once that artifact is excluded, the real pattern of IA-code reuse across firms is modest (max 12 firms). Separately, pd_tr_name is confirmed to be far too generic to identify individuals.

Verified fact: The relationship is many-to-many in both directions, though asymmetric — 21.8% of IA codes have multiple access IDs, while only 0.6% of access IDs have multiple IA codes. This means neither field cleanly identifies "one individual" on its own: an access ID occasionally spans multiple IA codes (117 cases, up to 53), and an IA code commonly spans multiple access IDs (3,278 cases, up to 449). An access ID therefore cannot be assumed to represent exactly one individual — it is associated with multiple IA codes in a small but non-trivial number of cases, and the underlying business reason (shared system login vs. data error) is not determinable from this table.

Verified fact: pd_tr_name is confirmed not reliable for identifying an individual. With only 489–616 distinct name values spread across 15,063 IA codes and 36,815 rows, the overwhelming majority of names are shared across many different, unrelated IA codes (72% of names, averaging 31.5 IA codes per name, up to 611). This is consistent with pd_tr_name being a generic, templated, or non-unique field (e.g., a placeholder, title-only, or truncated/standardized value) rather than an individual's actual name — though the exact cause (masking, data entry convention, or genuine common names) cannot be determined from this table alone and should be treated as an open question, not a confirmed root cause.
4. Unusually large firm counts per IA code — resolved as a data artifact
Firm-count threshold	IA codes exceeding it
> 2 firms	2,850
> 5 firms	376
> 10 firms	4
> 20 firms	1 (the 229-firm case)
4
Root cause identified and verified: Isolating by code content shows the single IA code with 229 firms is an empty string (""), length zero — not a real IA registration code. Excluding this one blank value, the maximum firm count among genuine (non-empty) IA codes drops to 12, and only 3 real codes exceed 10 firms 5.
For the remaining real high-firm-count codes (11–13 firms each), a spot check of status and date fields shows these rows are all agent_status_code = '00' (Inforce) with no populated status_change_date, and no termination_effective_date on these particular groupings 6. This means the data shows these as concurrently in-force relationships across multiple firms, not resolved via different historical periods — but whether this reflects genuinely simultaneous active appointments or stale/unclosed records cannot be confirmed without transaction-level history, which is not available in this table.
Conclusion: The extreme 229-firm case is a NULL/blank-code artifact and should be excluded from any IA-code-based analysis (filter out empty-string pd_tr_ia_code, not just NULL). Genuine IA-code firm-sharing is real but modest in scale (rarely above a handful of firms).

Verified facts:
Only two pd_tr_status values exist in the data: T and I (undocumented codes — business meaning not provided in the schema and not invented here).
pd_tr_status does not perfectly align with agent_status_code: both T and I statuses appear under both in-force (00) and terminated (51, 61) agent statuses, confirming these are two independent fields, not duplicates of each other.
The large majority of PD-TR rows (36,197 of 36,815, ~98.3%) carry agent_status_code = '00' (Inforce), meaning the vast majority of records represent currently in-force relationships rather than historical/terminated ones — but a nontrivial number (652 rows) are terminated and remain in the table, confirming historical/inactive records are not excluded from this dataset.
IA-code completeness differs materially by pd_tr_status: rows marked I are 97.5% complete for IA code, while rows marked T are only 76.8% complete. This suggests pd_tr_status may relate to a verification or confirmation stage (hypothesis, not confirmed), since the less-IA-complete group (T) could represent earlier-stage or less-validated records — but the exact meaning of T vs. I is undocumented and should not be assumed.
What remains unresolved
No field investigated so far — pd_tr_ia_code, pd_tr_access_id, pd_tr_name, or pd_tr_INTTRAGTSEQ — has been shown to cleanly and uniquely identify one individual technical representative without exceptions. pd_tr_ia_code remains the most plausible individual-level credential (after excluding the blank-string artifact), but it still shows multiple access IDs per code in 21.8% of cases and is only 85% populated overall (31,182 of 36,815 rows). Given these unresolved inconsistencies, no final unique technical-representative counting rule is recommended; any such rule should first exclude blank/empty-string pd_tr_ia_code values and should be validated against the source IA registry or aa_tbltragent system before being adopted as a business metric.
